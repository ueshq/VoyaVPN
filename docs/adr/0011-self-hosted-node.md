# ADR 0011: Self-Hosted Node

Status: Accepted

Date: 2026-09-19

## Context

Users with a device outside mainland China (a home computer or a cloud
server) want to run their own exit node on it and connect to it from devices in
mainland China, without renting a commercial service or operating a server
stack by hand. The device already ships the sing-box core, which contains the
VLESS, REALITY and Shadowsocks server inbounds.

Three questions had to be settled: where the server runs relative to the
connection core that ADR 0005 governs, where its secrets live, and how the app
learns whether other devices can reach it.

## Decision

### A core of its own

The node is a **separate sing-box process**, not an inbound added to the
connection config:

- An overseas exit normally runs while its own VPN is disconnected, so the
  connection core is often not running at all.
- On macOS the connection core is the PacketTunnel provider (ADR 0005); an
  inbound there would only exist while the VPN is up, and the server's egress
  would go through the user's own proxy.
- On Windows the connection core runs as SYSTEM inside the tunnel service;
  the node would then listen as SYSTEM.

`voya-app::self_host` supervises the process on a **dedicated
`ProcessRunner`**: a runner has one exit-handler slot, and the connection
core's belongs to the supervisor. It gets the same kill-with-the-app job object
as the other cores. On macOS it launches the signed seed in place, exactly like
the disconnected latency test, and inherits the app's sandbox, which already
carries `com.apple.security.network.server`. ADR 0005 is unchanged: the node is
never a connection core and never carries this device's own traffic.

The config is generated by `voya-core::singbox::selfhost` from a typed
`SelfHostSpec` and pinned by golden fixtures (ADR 0003): dual-stack server
inbounds on `::`, `sniff` → `resolve` → reject loopback, link-local, cloud
metadata and multicast destinations, reject private networks unless the user
allows LAN access, optionally reject BitTorrent, then `direct`. Resolving before
the address rules is what keeps a domain that points at a private address from
reaching this device's network. `auto_detect_interface` binds egress to the
physical interface.

Protocols are VLESS + REALITY with XTLS Vision (the default) and Shadowsocks
`2022-blake3-aes-128-gcm`. Share links carry `fp=chrome`, and REALITY clients
always get uTLS: sing-box refuses a REALITY client without it.

### Secrets stay in the backend

The node's record — settings plus the VLESS UUID, the X25519 private key, the
short id and the Shadowsocks key — is one strict JSON row in a new `self_host`
table (`voya_contracts::SelfHostRecordV1`). It never crosses IPC: the renderer
receives the finished share links and nothing that would let it impersonate
the node. `AppSettingsV1` was rejected as the home because the whole DTO
round-trips through the renderer on every settings save, which would expose the
private key and let a stale save overwrite freshly rotated keys.

The table changes the database baseline from 0010 to 0011 (ADR 0001, 2026-09-11
amendment): existing databases are moved aside through the startup dialog.

Keys come from the platform CSPRNG in `voya-app` (`x25519-dalek`, `getrandom`);
`voya-core` stays deterministic and receives them as data.

### Reachability: detect and explain, never relay

The page explains whether other devices can reach the node:

- interface addresses from `voya-platform::netif`;
- the public address and an external TCP probe from a stateless Cloudflare
  Worker (`apps/probe`) that only ever connects back to the caller's own
  address (`CF-Connecting-IP`), per address family;
- UPnP IGD port mapping (`voya-net::portmap`), renewed by a watch loop, which
  also reveals double and carrier-grade NAT through the router's WAN address;
- the Windows Firewall rule for the core, added on request behind UAC
  (`voya-platform::firewall`);
- a **self-test**: a throwaway probe core on this device imports the node's
  own share links (pointed at loopback) and fetches a page through each
  protocol. REALITY can fail silently: a disguise site that speaks TLS 1.3 can
  still refuse the borrowed handshake (`www.microsoft.com` did with sing-box
  1.13.14 in 2026-09), and the node then treats every peer as an
  unauthenticated visitor while its port looks open to any probe. The default
  disguise site is one that was verified (`www.apple.com`), and the self-test
  catches a bad choice the user makes later.

`self_host::environment::classify_family` turns the evidence into a typed
verdict and reason codes the frontend translates. There is no traffic relay,
no hole punching and no registry: links are distributed by copy or QR code,
and the user supplies a DDNS name when the public address is dynamic. The app
warns when the detected address changes.

## Consequences

- The probe Worker is operated by VoyaVPN on a custom domain (workers.dev is
  unreachable from mainland China). When it is unreachable, the page falls back
  to an inferred verdict and says so.
- A probe from Cloudflare proves the node is reachable from the internet, not
  that the route from mainland China is fast or unblocked.
- While this device's own tunnel is up, neither the public address nor the
  probe describes the node's path; the check reports `tunActive` instead of a
  verdict.
- The node is down while the device sleeps. On macOS and Linux a crashed app
  can leave the node core running until its port is needed again (no process
  group reaping); the next start reports the port as in use.
