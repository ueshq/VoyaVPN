# ADR 0006: Priority Proxy Domain List

Status: Superseded by ADR 0009 (2026-09-13)

Date: 2026-09-08

## Context

VoyaVPN's Rule mode routes traffic with the user's own rule table plus the
shipped geo assets. A class of vendor endpoints breaks under that default:
AI and developer-tool providers (Anthropic, OpenAI, GitHub Copilot, Google
Gemini, and similar) geo-block, rate-limit, or hard-fail a direct connection
from the regions this app targets. A rule table that sends those names direct
therefore does not produce a faster path, it produces a tool that returns
errors, and the failure looks like a VoyaVPN bug rather than a routing choice.

`crates/voya-core/src/singbox/mod.rs` answers this with
`PRIORITY_PROXY_DOMAIN_SUFFIXES`: a hardcoded list of domain suffixes that
config generation always forces through the proxy. It has no settings field, no
IPC surface, and until now no written rationale, so neither users nor
maintainers could tell whether a domain is on it by policy or by accident.

## Decision

The list stays in `voya-core`, hardcoded, and is documented rather than
configurable:

- `crates/voya-core/src/singbox/routing.rs` emits exactly one route rule
  (`domain_suffix` → the `proxy` outbound) from the list, and
  `crates/voya-core/src/singbox/dns.rs` emits exactly one DNS rule
  (`domain_suffix` → the remote DNS server) so the names are not resolved by
  the direct resolver first.
- Both rules are appended **after** the `clash_mode: Global`
  rule and **before** the user's own rules. Mode selection therefore still
  wins; inside Rule mode the list wins over the user's rule table.
- The list is a compile-time constant because generation must stay a pure,
  deterministic function of the profile and app config (ADR 0001, ADR 0003).
  Keeping it in `voya-core` puts it inside the golden-fixture parity contract,
  where a change to it shows up as a reviewable diff in generated sing-box
  JSON, instead of in per-machine user data that no fixture can pin.
- Making it user-editable is a contract change — a `voya-contracts` DTO field,
  a `voya-db` column, an IPC/settings surface, and a settings UI — and is
  deliberately out of scope for the constant itself. It is not blocked by this
  ADR; it is simply not part of it.

## Consequences

- The list overrides user routing intent inside Rule mode. A user rule that
  sends `openai.com` direct is generated *after* the priority rule and never
  matches. That is intentional, and it is the single most surprising behavior
  in the generated route table.
- Names on the list are always resolved through the remote DNS server, even
  when the user's DNS rules would resolve them directly.
- Direct traffic mode has been removed from Home, IPC, and generated route/DNS
  rules. Per-domain configuration is still unavailable:
  - `Global` mode proxies everything anyway, so the list is a no-op.
  - Stopping the core, or turning off TUN and the system proxy, removes the
    behavior with the rest of the routing table.
  - There is no way to keep Rule mode and send one of these suffixes direct.
    That gap is the known cost of this decision and the reason a settings-level
    opt-out is expected to follow.
- Editing the list changes generated JSON. The route/DNS ordering is pinned by
  `singbox_priority_proxy_domains_follow_clash_mode_and_precede_user_rules` in
  `crates/voya-core/src/singbox/tests.rs`, and any fixture under
  `tests/golden/singbox/**` that captures those rules must be regenerated by
  hand in the same change.
- When a user-facing opt-out lands, the constant becomes the default seed for
  that setting and this ADR must be updated to record the new contract.
