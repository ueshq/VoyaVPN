# 性能优化:speedtest 事件 rAF 合并 + connections 面板预计算

两项纯前端改动,无 Rust/IPC 契约/bindings/e2e fixture 变更。

## 变更 1:speedtestResult 事件 rAF 合并(收益最大)

**问题**:Rust 每个节点发一个 `speedtestResult` 事件(`crates/voya-app/src/speedtest/manager.rs:208`,默认 page_size=1000,整轮背靠背),前端 `apps/desktop/src/ipc/runtime-event-store.ts:214-220` 每事件 spread 整个 `speedtestResultsByProfileId` 新对象 → `use-node-list-data.ts` 全量 remap → `node-list-rows.ts` 全量重组+组内排序。N 节点测速 = O(N²) UI 线程重算;该路径是三条高频流中唯一没接 rAF 合并的。

**改动**(全部在 `apps/desktop/src/ipc/runtime-event-store.ts`,镜像现有 logLine 缓冲模式 157-181 行):
1. 模块级新增 `pendingSpeedtestResults: Record<string, SpeedtestResult>` + `pendingSpeedtestResultsFrame: FrameHandle | null`(声明在 79-87 行现有缓冲旁)。
2. `pushTransientEvent` 把 `speedtestResult` 从通用 `set` switch 拿出,放 logLine 分支旁:入缓冲(同 indexId 后到覆盖,与现语义一致),`scheduleFrame` 一帧 flush——换出缓冲、空批 early-return、单次 `set` 合并 `{ ...state.speedtestResultsByProfileId, ...batch }`。
3. `clearSpeedtestResults`(251 行)同步清空 pending 缓冲(镜像 `clearLogs` 对 `pendingLogLines` 的处理),防止 run 结束 invalidation 清空 store 后已调度帧复活旧结果。

**明确不做**:Rust 侧批量发射(需加枚举变体+bindings+e2e mock,前端合并已把 O(N²) 折叠为每帧一次);event-bridge 1s country-refresh trailing 合并保留(国旗只能来自持久化快照的语义依赖它)。

**测试**(`apps/desktop/src/ipc/runtime-event-store.test.ts`):
- 改写 "stores speedtest result events without ending the running state"(62-86):fake timers 下 push 后同步断言不变,`advanceTimersByTimeAsync(20)` 后断言合并结果。
- 新增镜像用例(参照 180-254 proxyConnections/logLine 测试):突发多结果+同 id 覆盖 → 一帧一次 set;clear 在帧执行前调用 → pending 丢弃、空批 no-op。
- 覆盖率注意:`ipc/runtime-event-store.ts` 有 65/50 ratchet,新分支全部由上述用例覆盖。
- 风险核查:确认 `speedtestResultsByProfileId` 消费者(use-node-list-data 选择器、event-bridge 的 clearSpeedtestResults)无同步可见性依赖;event-bridge.test.tsx 对 store 是 mock,不受影响。

## 变更 2:connections 面板预计算搜索/排序键

**问题**:`apps/desktop/src/features/proxy/connections-panel.tsx:97-129` 的 rows useMemo 每次快照推送(约 1 次/秒,最多 1 万行)重跑:搜索时每行重建 10 字段+chains 的 join/lowercase;route 排序每次比较调 `connectionRoute`(每次 3 个中间数组)+ `routeLabel`(含 `t()`)+ `localeCompare`,共 O(n log n) 次;needle 每次击键也触发全量重建。

**改动**(保持 rows 元素类型仍为 `ProxyConnectionItem[]`,渲染代码零改动):
1. 提取纯函数 `connectionSearchHay(connection): string`(现 filter 内的 `[host, source, destination, process, processPath, rule, rulePayload, network, connectionType, ...chains].filter(Boolean).join(" ").toLowerCase()` 原样迁移),放 `features/proxy/` 下与 `connection-route.ts` 同级,配套单测。
2. 拆分 useMemo:
   - `hays`:`searching = filter.trim().length > 0` 为真时按快照 `map(connectionSearchHay)`,deps `[snapshot.connections, searching]` —— haystack 每快照算一次,击键不再重算;
   - `routeTexts`:仅 `sort?.column === "route"` 时按快照预计算 `routeLabel(connectionRoute(c), t)`;
   - rows useMemo 退化为:局部 `derived = connections.map((connection, i) => ({ connection, hay, routeText }))` → filter(读 hay)→ sort(比较器读预计算值:traffic 数值比较、route 预计算字符串 localeCompare、host/process 直接 localeCompare)→ `.map((row) => row.connection)`。
3. 行渲染(324-401 行,可见行约 30)保持现状,不预计算全量 route——避免无 route 排序时反向劣化。

**明确不做**:后端增量推送(搜索/排序将跨 IPC,交互劣化);Rust 侧截断(前端 10_000 只是校验上限,截断会静默改契约)。

**测试**:新增 `connectionSearchHay` 单测(字段拼接、null 过滤、chains 展开、大小写);现有 `connections-panel.test.tsx` 排序/搜索/route chip 测试(92-119、366-378)行为不变应保持通过;参照 `server-table.test.tsx:268-291` 先例加一条 10k 行 route 排序+搜索的时长预算用例(CI 抖动则降级为纯函数用例)。
